Anchor: executive summary

Team Beacon · Orange County Claude Impact Lab · October 17, 2026 · Challenge 1 (referral intake), built for Illumination Health + Home (IHH)

Anchor helps IHH's intake team read hospital referrals faster and surer, keep hospitals informed, and answer inside the 2-hour promise.

Who IHH is

A Santa Ana nonprofit that pairs housing, healthcare and case management for people experiencing homelessness (IHH website). Its recuperative care gives people leaving the hospital a safe place to heal: people too sick for the street, but not sick enough to stay in a hospital. Studies link recuperative care to fewer hospital days and readmissions. California's Medicaid agency found a 29.2% net cost reduction (preliminary). IHH served 2,287 people in recuperative care in 2024. More in ABOUT-IHH.md.

The problem

  • Hospitals refer patients to recuperative care with referral packets. Packets run 14 to 34 faxed pages (the Challenge 1 README rounds this to 15 to 35), often crooked, sideways or out of order, and at least one has no IHH referral form.
  • A coordinator reads each packet by hand against IHH's criteria (155 rules). The deciding fact is often deep in the chart, not on the form.
  • IHH promises hospitals an answer within 2 hours. Hospitals send the same referral to several providers, so a slow answer can mean a patient leaves with nowhere to go.

What Anchor does

  1. Rule overlay: IHH's 155 rules, tagged so a tool knows:
    • 9 rules that need a date. Dates are redacted, so the tool says "can't tell" instead of guessing.
    • 26 places where the written rules are unclear. These go to a person.
    • where the evidence usually is, and which of 27 core facts each rule depends on
  2. Verification checklist: a fillable, printable form (5 pages, 151 fields) with a Great / Neutral / Bad completeness grade, a to-do list of missing items, and a Verified box for every fact.
  3. Anchor Board:
    • a queue sorted by patient-need priority, with a 2-hour answer clock
    • a to-do list for every incomplete packet
    • a packet view with summary, missing information, medications, history and an email log
    • staff and IT guides, and accessibility built toward WCAG 2.2 AA (not yet tested with assistive-technology users)
  4. Anchor intake app:
    • takes referrals in any common format, including fax-to-email
    • sends a receipt at 0 minutes, requests missing items at 30 and 60, and escalates at 60, 90, 110 and 120
    • raises red flags immediately: to the clinical reviewer at once, and to the hospital as soon as a clinician confirms, so the question is answered before the clock runs out

Why it can be trusted

  • Every rule is cited by IHH's own ID. Every fact must point to a page. "Unknown" and "can't tell" are real answers.
  • People decide. The tools never approve or deny.
  • Nothing is sent, and the real packets are never published. Messages are drafts in an outbox. With an API key, page images (pre-read) and referral details (Ask Anchor) go to the Claude API, so use only de-identified data.
  • Checked:
    • 48 automated tests pass
    • an independent verifier moved the rule work from FAIL to PASS WITH FIXES
    • IHH's real decisions are held out for scoring only

Anchor: referral intake app (prototype)

Anchor, by Team Beacon. A local app for IHH's referral intake team. Referrals arrive in any format. Claude reads the packet straight away. Staff check the facts with each page beside it. The hospital is kept informed inside the 2-hour promise.

Try it online first: the Anchor Board (opens in a new tab) runs in the browser on made-up sample packets, with nothing to install.
Dry run only. Nothing is ever sent. Every message is written to outbox/ as a file marked DRY RUN. Files stay on this computer.

Start it

cd saturday-oct17-build/intake-pipeline
python3 make_samples.py                      # made-up sample faxes (and demo answers)
INTAKE_PORT=8777 python3 server.py           # open http://127.0.0.1:8777
  • Turn on the real pre-read and Ask Anchor: set ANTHROPIC_API_KEY before starting, or put ANTHROPIC_API_KEY=... in intake-pipeline/.env (git-ignored; the app reads it on its own).
  • Without a key: the made-up samples use built-in demo answers. Any other file opens in "review by hand" mode.

Needs Python 3.9 to 3.12 (the server uses the cgi module, which Python 3.13 removed), Pillow, pypdf, and pdftoppm (poppler). Turning Word files and iPhone photos (HEIC) into readable pages uses macOS tools (textutil, sips), so on Windows or Linux those files are marked "ask the hospital to resend".

Try it in 2 minutes

  1. Type your name and role in Working as at the top and press Save. Every action except the demo clock needs a name, so the history shows who did what.
  2. Press Check fax inbox. Two made-up faxes become two referrals, and both are read straight away.
  3. Open the first one (graded Bad). At the top, What to do next says what to do.
  4. Step 1, To-do list:
    • Press Confirm on the possible red flag. The hospital is told right away.
    • Press Send request now for the missing items.
  5. Step 2, Check the facts:
    • Press J to move through the facts. Each page shows beside its fact.
    • Press V to mark a fact verified.
    • The "Cognitive impairment" fact shows two pages side by side, because the form and the chart disagree.
  6. Step 3: press Demo: hospital resends missing pages. The new pages join this referral, and the medication list and vitals items close themselves.
  7. Open the second referral. It's Great, so it gets the Fast lane: one screen to decide.

Upload, and who's working on what

  • ⬆ Upload (top of every page): start a new referral from files. To add pages to an existing referral, use Add more files on its page.
  • Working as: each person's name is saved in this browser and recorded on every action.
  • Status on the list: Untouched (no one has opened it), Opened by (viewed only), Worked on (someone acted), plus a Worked on by column.
  • Step 6, Who has worked on it: the full history for that referral, newest first.

Ask Anchor (the helper)

A chat panel on every page, powered by Claude Haiku. It knows which page, section and fact you're looking at, and suggests the next step by naming the button or key.

  • It answers only from Anchor's own guide and the referral on screen. It never gives medical or eligibility advice.
  • If it mentions a rule ID that isn't in IHH's rules, its answer is replaced by the built-in next step.
  • Without a key it shows the built-in "What to do next" instead.
  • It sends the on-screen referral's details (status, facts, to-dos, no page images) to the Claude API. Use only made-up or de-identified data.

What the pre-read never does

  • Decide. It suggests; staff verify and decide.
  • Guess a date. Rules that need one say "can't tell".
  • Call a black box missing. It's a redaction.
  • Use a rule ID that isn't in IHH's rules. Made-up IDs are dropped.
  • Send a request staff haven't approved. A possible red flag reaches the hospital only after a clinician confirms it.

About Illumination Health + Home (IHH)

Who IHH is, what it does, and how it helps people and Orange County. Each fact names its source, and IHH's own claims are marked as IHH's.

Who IHH is

  • A nonprofit based in Santa Ana, known until 2025 as Illumination Foundation. (event background, docs/background.md)
  • Founded in 2008 as The Illumination Foundation. (IHH website, home page)
  • Its mission, in its own words: "to disrupt the cycle of homelessness by providing healthcare, housing, and hope—together." (IHH, Mission and Vision page, via docs/background.md)
  • It serves people experiencing homelessness across Orange County. (IHH website)

What IHH does

IHH pairs housing with healthcare and case management, which it calls "full-circle care". (IHH website)

ProgramWhat it is

How it fits into the health system

  • The law: California law requires hospitals to plan discharge for patients who are homeless and to find a destination, giving priority to a sheltered one with supportive services. The hospital must send the receiving provider information about the patient's care needs. That information is the referral packet. (Health and Safety Code 1262.5, via docs/background.md)
  • Who pays: Medi-Cal health plans can pay for recuperative care as a "Community Support." In Orange County that plan is CalOptima Health:
    • stays are authorized 30 days at a time
    • up to 90 consecutive days
    • each renewal needs the client's care plan

(CalOptima Health provider guide, January 2026, via docs/background.md)

  • The promise: IHH tells hospitals it will answer a referral within 2 hours. (IHH referral form RC0725)

Why it matters in Orange County

  • Orange County counted 6,321 people experiencing homelessness in January 2026, and 3,065 of them were unsheltered. (County of Orange)
  • Among unsheltered adults, about a third reported a physical disability and about a third a serious mental illness. (2026 Point in Time Count report)

These are the people most likely to land in a hospital and have nowhere safe to recover.

How Anchor helps IHH help people

Hospitals refer patients to recuperative care, and IHH promises an answer within 2 hours.

  • Faster, surer answers. The verification checklist, rule overlay and triage board help coordinators find the deciding facts in long faxed packets. They show what's missing and look first at the patients who need it most.
  • Fewer patients discharged with nowhere to go. The intake pipeline keeps hospitals informed at every step. Red flags reach the clinical reviewer right away, and the hospital as soon as a clinician confirms, so questions are answered before the clock runs out.
  • More time for people, less for pages. Coordinators spend less time hunting through paper and more with patients and hospital partners.

Anchor is a prototype built by Team Beacon. A coordinator makes every decision.

Three-minute demo script

  1. Before you start: type your name in "Working as" at the top and press Save. Every action except the clock needs a name.
  2. Problem (25 s): "A long, sideways fax. Two hours to answer. The deciding fact is often deep in the chart, not on the form."
  3. Intake (35 s): Drop a fax email into the inbox and press Check fax inbox. It becomes a 3-page PDF, and the receipt is written to the outbox.
  4. Red flag (30 s): Add a red flag. A staff-added red flag tells the intake team and the hospital immediately; one the pre-read finds goes to the clinical reviewer first and reaches the hospital only after they press Confirm. Open the hospital one: "This is not a decision."
  5. Clock (20 s): Advance the clock: requests at 30 and 60, escalation at 60, 90, 110 and 120.
  6. Triage Board (40 s): Show the queue sorted by patient need. Open a Bad packet: missing information first, priority points, the to-do list with rule IDs.
  7. Trust (30 s): Show the verification checklist, the verifier going from FAIL to PASS WITH FIXES, and one line on what's mocked.

How grading works

The grade says how complete and consistent a packet is. It never says whether the patient qualifies. A person always decides.

Step 1: score the 27 facts

  • Found (with a page): 2 points
  • Unclear, or Can't tell (the rule needs a date, and dates are blacked out): 1 point
  • Missing: 0 points
  • Redacted (a black box): not counted. A black box is privacy, not a gap.

Fact score = points ÷ (2 × facts that apply), shown as a percent.

Step 2: pick the grade

  • Great: all 7 core documents (IHH form, face sheet, CalOptima form/LOA/authorization (DOC-3), H&P, vitals, medication list, PT/OT or nursing notes), a fact score of 85% or more, and no conflicts. Ready for a person to decide.
  • Bad: any critical alert (a rule that would exclude the patient looks true), a missing core document, or a score under 60%. Call the hospital before deciding.
  • Neutral: everything else. Request the specific items.

When a packet is incomplete

A Neutral or Bad packet comes with a to-do list. Each item starts with what to do:

  • Clinical review: someone clinical reads the page before anything else.
  • Get: ask the hospital for a missing document.
  • Find: the document is there but the fact isn't. Look again or ask.
  • Settle: the form and the chart disagree. Open both pages and decide which is right. Anchor's default is to trust the chart over the form; that is a team choice, not an IHH rule.
  • Confirm with hospital: the rule needs a date we can't see.
  • Coordinator decides: IHH's written rules don't settle it.

Priority: who to look at first

Priority is about the patient's need, not completeness: discharge today +3 (tomorrow +2), answer clock Late +3 (At risk +2), unhoused +1, high care need +1, recent repeat episode +1. P1 Urgent is 6 or more points, P2 High 3 to 5, P3 Routine 2 or less. Answered packets show Done.

The answer clock

IHH promises hospitals an answer within 2 hours. On time is up to 90 minutes, At risk is 91 to 120, and Late is after 120. Answered packets show Answered.

Staff guide: using the board

For referral coordinators and nurses. Every packet on this board is made up.

1. Start with the queue

On the Board tab, work from the top: the queue is sorted by priority (P1 Urgent first), then by time waiting. Watch the answer clock.

2. Open a packet

Click a packet name. Its details open in a pop-up: summary, key missing information, priority with its points, made-up patient details, the mock fax PDF, the email log, the packet page by page, medications, and medical history. Press Esc or Close to go back to the queue.

3. Look at the grade, then the to-dos

  • Great: everything needed is there; a person can decide.
  • Neutral: ask the hospital for the listed items.
  • Bad: read the critical alerts first, then call the hospital.

4. Check the page yourself

Each alert names its page. Read that page before relying on it. A tool can misread a crooked fax.

5. Ask the board

Below the queue, Ask the board explains grades, priority and what to do first for the selected packet: the one you last opened, or the top of the queue until you open one. It never says whether a patient qualifies.

6. Decide

You decide. Anchor never approves or denies. The board sends no messages; in the intake app, messages are dry-run drafts.

Keyboard

  • Tab moves between controls; the first stop is "Skip to content".
  • On the tabs, ← → switch tabs; Home and End jump to the first or last.
  • In the queue, each packet name is a button. Enter opens its pop-up; Esc closes it and returns you to the same packet.
  • The ☰ Menu button (top right) opens the guides. ↑ ↓ move through it; Esc closes it.

Remember

  • A black box is privacy, not a missing document.
  • "Can't tell" means the rule needs a date we can't see. Ask the hospital if it matters.
  • Sex offender status is case by case (rule OTH-2). Never auto-deny.
  • Never type names or record numbers into notes.

IT guide: how this page works

For whoever sets it up and keeps it running.

What it is

One self-contained HTML file, ANCHOR.html, built by build_anchor_page.py from the team's docs and the made-up sample files in triage-dashboard/. Rebuild with python3 build_anchor_page.py; it also runs the tests and shows the result on the Checks tab.

Ask the board, three ways

  • On claude.ai: the page asks Claude through the artifact's sample capability, on the viewer's own account, after they allow it.
  • Locally with Claude: run python3 board_server.py and open http://127.0.0.1:8790. If a key is set (in the environment or intake-pipeline/.env), the server calls Claude Haiku by default. The key never reaches the browser. The server binds to 127.0.0.1, refuses requests for any other host name and questions from any other page, and serves only an allowlist: this page, its mock fax PDFs and the files listed under Everything we made.
  • Anywhere else: built-in answers from the same rules.

Every Claude answer is checked before it shows: an answer that names a rule ID that isn't one of IHH's 155, or uses common wording that reads as an admission decision ("qualifies", "eligible", "should be approved"), is replaced with the built-in answer. The check catches common phrasings, not every possible one; a person still decides.

Data the board needs

Packets: packet_id, hospital, received, minutes_open, status, pages, required_docs_present, docs_present, facts_applicable, facts_found, facts_unclear, facts_cant_tell, facts_missing, facts_verified, critical_alerts, contradictions, minutes_to_ready, missing_docs

Alerts: alert_id, packet_id, type, what, rule_id, page. Profiles, pages, medications, history and the email log are in the matching sample-*.json files.

Rules that don't bend

  • No real patient details on any published page. Real packets stay on a staff computer.
  • Never connect to IHH's live systems in the prototype.
  • The board sends nothing; the intake app writes dry-run drafts only.
  • API keys go in environment variables or the git-ignored .env, never in code.

Accessibility

Built toward WCAG 2.2 AA: tabs follow the ARIA tabs pattern, the menu works by keyboard, packet details use a native dialog that returns focus, tables have captions and headers, links that open a new tab say so, colors come from light and dark tokens, and the page shows every section if JavaScript is off. Not yet tested with screen-reader users or a formal audit.

How Anchor was built

Team Beacon's build story for Anchor, our referral intake tool for IHH: what we started from, what we read, the order of work, the tools, how we checked it, and what we chose not to do. Written so IHH or another team can pick it up.

Scope: Challenge 1, referral intake.

The starting point

We began with a Packet Triage design and build plan written before the event. It was thorough, but written for a generic setting, with synthetic data and invented rules.

Step by step

1. Learn who IHH is

  • We read six pages of IHH's public website: home, Get Help Now, housing services, healthcare services, about, and contact.
  • We noted IHH's programs, its Orange County service area, its published intake routes, and some inconsistencies on the site (board chair names, rating figures).
  • We re-aimed the plan at IHH: its roles, its locations and its recuperative care intake.

2. Read the event's Challenge 1 materials, carefully

  • We read IHH's admission criteria (155 rule IDs), the referral form, and the packets README.
  • We began reading the 11 real de-identified packets.
  • The event rules say to stop and tell an organizer about any possible missed identifier. We stopped and flagged it. An organizer later confirmed it is fine, so the review can resume.
  • While paused, we built a fillable, printable verification checklist (5 pages, 151 fields) from the public criteria only. It includes a field map showing which facts both forms ask, which only one form asks, and which only the chart can answer.
  • We rewrote the plan for the real conditions:
    • image-only faxes
    • IHH's rule IDs
    • five statuses: Found, Unclear, Missing, Can't tell, Redacted
    • a completeness grade of Great, Neutral or Bad
    • IHH's decisions held out from the tool

→ 01-packet-triage-v2.md

3. Build the Anchor Board (on made-up samples)

  • The real packets can't go on a published page, so we wrote 10 clearly labeled made-up sample packets.
  • The board shows:
    • a queue with a 2-hour answer clock
    • grades, with a to-do list for every incomplete packet
    • a priority based on patient need (P1 Urgent, P2 High, P3 Routine)
    • a click-through packet view: summary, missing information, priority points, patient details, a mock fax PDF, an email log, page map, medications, and history with recent episodes
    • staff and IT guides in plain words
  • Accessibility: we added a WCAG 2.2 AA layer:
    • keyboard tabs and skip links
    • focus that survives redraws
    • captions and row headers on tables
    • announcements for screen readers
    • a symbol and a word with every color
    • high-contrast mode, reduced motion, and larger tap targets

4. Add an independent checker

  • We wrote an ihh-verifier subagent. It breaks work into claims, checks each one against its primary source, enforces 12 hard rules, and writes a prioritized correction plan.
  • We built a criteria overlay adding the fields a tool needs to all 155 rule IDs: type of rule, date-dependent rules, gaps in the written rules, where evidence lives, and links to the 27 core facts. It also turns the children's criteria into JSON.
  • The verifier's first run said FAIL:
    • two wrong claims in the organizer note
    • wrong fact links on ID-2 and ID-3
    • seven smaller issues
  • We fixed the main items. The second run said PASS WITH FIXES, after rebuilding the files independently and getting byte-identical results.

5. Build the intake and follow-up pipeline

  • A local web app that accepts PDF, multi-page TIFF faxes, photos (including iPhone HEIC), Word, text, email and zip.
  • It identifies files by their contents, never runs them, and turns faxes and photos into PDFs.
  • Fax-to-email runs through an inbox folder that stands in for the mailbox.
  • Tiered follow-ups inside the 2-hour promise:
    • receipt at 0 minutes
    • requests for missing items at 30 and 60
    • escalation at 60, 90, 110 and 120
    • immediate red-flag messages: a flag staff add goes to the intake team and the hospital at once; a flag the pre-read finds goes to the clinical reviewer at once, and to the hospital once a clinician confirms it
  • Every internal message goes to the IHH Referral Intake team. A "for:" line says which role should act.
  • Dry run only: every message is a file in outbox/.
  • 48 unit tests pass (cd intake-pipeline && python3 -m unittest discover -s tests -t .), and a full end-to-end run produced every tier in order.

How we kept it honest

  • Sources first. Every rule comes from IHH's criteria by ID. "Unknown" is a real answer.
  • The math was run, not trusted:
    • the grading and priority code was run on the samples
    • the overlay was rebuilt and compared
    • the pipeline has tests
  • Made-up data is labeled everywhere it appears.
  • An independent verifier checked the overlay, and we fixed what it found.
  • We reported our own mistakes:
    • an invented rule ID in an early draft was replaced with the real one (NEU-X5)
    • a quote bug that would have broken the board was fixed before publishing
    • wrong rule IDs in the sample alerts were corrected against the criteria file

What we chose not to do, or couldn't

  • No real sending. Email and fax senders are stubs that refuse to run, as the event rules require.
  • No real packets on any published page. The board uses made-up samples. Real packets stay local.
  • No peeking at IHH's decisions. Only a scorer opens that file, and only after all reviews exist.
  • The packet review paused until an organizer cleared a question about one packet (cleared Oct 17; not yet resumed).
  • The automated packet copy was blocked by a safety check. The user copies the files by hand.
  • Not done: the team's own app (the remaining tasks in the plan), automatic links from the triage tool into the pipeline, fluent review of the Spanish, and testing with screen-reader users.
